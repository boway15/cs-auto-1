# 工作台邮件列表：日量 1000–2000 封时的加载策略

## 背景

全量 `select("*")` 拉取 `emails` 在 PostgREST 默认行数上限（约 1000）与传输体积上均不可持续。日增 1000–2000 封时，14 天窗口即可达 1.4万–2.8万 行。

## 已实现（前端）

| 项 | 说明 |
|----|------|
| 时间窗口 | 默认 **近 30 天**；可选 7 / 14 / 90 / 180 / 近 1 年 / **全部历史**（含超过 90 天的邮件，仍分页） |
| 分页 | 每页 **50** 条，`range` + `count: exact` |
| 列表字段 | 不含 `body_text` / `body_html`，详情在选中后单独 `select("*")` |
| 筛选下沉 | 状态、邮箱、分类、意图、关联状态、SLA 桶、关键词（发件人/主题/摘要/Message-ID）在服务端过滤 |
| Realtime | 1.5s 防抖，仅刷新当前页且尽量保持选中项 |

实现位置：`src/lib/workbench-email-list.ts`、`src/pages/Workbench.tsx`。

## 使用说明

- 日常：默认 **近 30 天**，可叠加「待处理 / 处理中」。
- **超过 90 天**：左侧队列时间范围选 **「全部历史」** 或 **「近 1 年」**，用底部 **上一页 / 下一页** 按收信时间倒序翻查；有单号或发件人时用搜索更快。
- 搜索仅在**当前所选时间范围**内生效。

## 运维建议

1. 保证 `emails(received_at DESC)` 有索引（迁移中通常已有 `idx_emails_*`）。
2. 「全部历史」数据量大时翻页会变慢，属预期；长期归档检索可后续做专用搜索（正文不宜 `ilike` 全表）。
3. 发送日志 / 拦截记录等页面仍为固定 `limit(200/500)`，与工作台独立。

## 后续可选

- 关联状态筛选完全服务端化（结合 `order_compensation_tasks`）。
- 虚拟滚动替代分页（单页条数很大时）。
- 列表只订阅 `pending/processing` 的 Realtime，降低刷新频率。
